# cases/{案件キー}.md 出力スキーマ

`docs/knowledge/cases/<案件キー>.md`（案件詳細ファイル）の **出力構造の正本**。
セクション見出しの種類・順序・各節の意味を定義する。

**課題の正式な記録**: 1課題1ファイルで、Git に入る（`docs/logs/` は作業場で Git に入らない）。最初の対応で作り、2回目以降の対応（再デプロイ・追加の対応・本番のリリース）でも**書き足す・書き直す**（「既にあればスキップ」はしない）。対応のたびに「## 対応履歴」に行を足し、ほかの節は最新の内容に書き直す（前の対応で分かったことは「## 調査・検討の経緯」と「## 対応履歴」に残す）。

> **参照方法**: backlog-releaser Step 3.8（/backlog）および sf-analyst-cat6 Step 5（/sf-memory）がこのスキーマを基準として生成する。抽出元データや経路固有フィールドは各エージェントが追加指定する。

---

## タイトル行

```
# <案件キー>: <件名>
```

- `<案件キー>` は Backlog の課題キー（issueKey、例: GF-123）
- `<件名>` は Backlog 上の summary / 件名（短縮不可・原文ママ）

## ヘッダ行

```
生成日: {YYYY-MM-DD} / 更新日: {YYYY-MM-DD} / データソース: <経路固有の値>
種別: <issueType>
```

- `データソース` と `種別` の値は呼び出し側エージェントが指定する
- `更新日` は書き足す・書き直すたびにその日にする（無い古いファイルは足す）。`生成日` は変えない
- cat6（Backlog 由来）では追加で `実績工数: {actualHours}h` 行を挿入してよい
- 空行をはさんでから `## TL;DR` に進む

## セクション定義（順序固定）

以下の8節を必ずこの順序で出力する。見出しの省略・追加・順序変更は禁止（中身が無い節は見出しを残して「なし」と書く。問い合わせの「## 調査・検討の経緯」「## 却下案・代替案」は「なし（問い合わせのため実装の検討なし）」）。

| 見出し | 記述内容 |
|---|---|
| `## TL;DR` | 200字以内の1段落要約。何の課題で・何をして・どうなったかを端的に述べる |
| `## 症状・要件` | 課題の事実部分（現象・依頼内容）を整形。箇条書き推奨 |
| `## 調査・検討の経緯` | 検討の流れ・確認事項・判断分岐の時系列。推定の場合は `[推定]` を付与 |
| `## 採用方針` | 最終的に何を選んだか・選定理由 |
| `## 却下案・代替案` | 排除した案と理由。情報が取れない場合は「なし」 |
| `## 教訓・再発防止` | 同様の問題を防ぐための知見。取れない場合は `[推定]` 付きで推測してよい（推測もできなければ「なし」） |
| `## 対応履歴` | 作業のまとまりごとに1行の表（下の §対応履歴）。対応のたびに行を足す（前の行は消さない・書き換えない） |
| `## 関連リンク` | Backlog 検索 URL ほか。呼び出し側エージェントが追加リンクを差し込んでよい |

## 対応履歴

```
## 対応履歴
| 日付 | 何をしたか | 結果 | 時間 |
|---|---|---|---|
| 2026-11-26 | 調査: 受注一覧の検索で日付の条件が逆になっていた（OrderSearchController.cls） | 原因を特定 | 1.5h |
```

- 1行 = 作業のまとまり1つ（調査・方針の決定・回答の作成・実装と確認・Sandbox への反映・操作手順の作成・テスト・証跡・本番の準備）。保守ポータルの課題では、ポータルに渡す対応の案と**同じ区切り・同じ内容**にする（二重に考えない。工数の正はポータル、cases は知見）
- 古い行が上（時系列）。前の対応の行は消さない・書き換えない
- **足し方**（`/backlog`・`/test`・`/release` のメインの会話が、作業のまとまりを終えるたびに行う〔[issue-source.md](./issue-source.md) §5「まとまりを終えたとき」の 3.〕。対応の案をポータルに渡すたびに同じファイルへ足して Git に送るので、途中の対応も残る。完了の仕上げは `/close`）:
  1. `python scripts/python/effort/effort_drafts.py pending {課題キー} --for cases` で、控えたのにまだ書いていないまとまりを出す（0件なら 5. だけ）
  2. 各まとまりを1行にする: 日付＝`workDate`・何をしたか＝`{label}: {content}`・結果＝そのまとまりの結論を短く（原因を特定・方針決定・Sandbox に反映・テスト PASS・手順書を作成 など）・時間＝`{hours}h`（担当者が手でやったらかかる時間。issue-source.md §5）
  3. `docs/knowledge/cases/{課題キー}.md` の「## 対応履歴」の表の末尾に足す（節が無い古いファイルは「## 関連リンク」の直前に節を作る。ファイルが無いときは `backlog-releaser` §3.8 の手順で作ってから足す）。ヘッダの `更新日` を今日にする
  4. `python scripts/python/effort/effort_drafts.py mark-sent {課題キー} --to cases {id}...` で印を付ける
  5. 最後に（足す行が0件でも）案件の記録を Git に送る: `python scripts/python/docs-sync/docs_sync.py "{コマンド名} {課題キー} の記録"`（コマンド名の先頭に `/` を付けない。Git Bash がパスに書き換えるため。例 `backlog GF-12 の記録`）。結果の1行をそのまま伝える。終了コードが 3（競合・手元の未保存の変更とぶつかった）・4（送り先が無い・docs 以外のまだ送っていないコミットがある・送信に失敗）のときは、やり直さず・force もせず、その1行と「記録はコミット済みです」を伝えて先へ進む（止めない）
- 本番のデータ（個人名・メールアドレス・取引の値）・お客さんの社外秘を書かない
