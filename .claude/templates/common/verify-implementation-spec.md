## 適用範囲・必須確認手順（core）

挙動・仕様・原因・**課題間の関係性**を答える / 対応方針を出す / 調査結果を報告するときは、記憶や推測で書かず、**必ず該当する実装コード・docs・実データ（SOQL）・Web を調べてから**、根拠を `ファイル名:行番号`（または docs パス）で示して回答する。確認できない範囲は `**[推定]**`／`**[要確認]**` を付け、根拠なしに断定しない（調査尽くしゲート通過後のみ許可）。

**調査尽くしゲート**: 「〜すればわかる」「〜を確認しないと断言できない」「実データを見ないと断定できない」と書きそうになったら、それは推論で締める合図ではなく、その手段を実行する合図。以下の手段を**すべて試した"これ以上は何もできない"状態でのみ** `[推定]`／`[要確認]` を許可する:
1. コード Grep / Read（`force-app/` 配下）
2. `docs/` 参照（catalog・design・overview・knowledge）
3. `sf data query`（実レコード値・件数・存在確認）/ `sf sobject describe`（項目の有無）
4. WebSearch / WebFetch（Salesforce 標準仕様・第三者製品の公式ドキュメント）
5. 組織直接問い合わせ（Tooling API `InstalledSubscriberPackage` 等）

**tools 制約**: 3・5 は `sf` CLI 実行（Bash tool）、4 は WebSearch/WebFetch tool が前提。自分の tools 一覧に該当ツールがない番号は「実行不可」として尽くした扱いにしてよい（未着手のまま放置ではなく、根拠欄に `[要確認: {手段名}は tools 未所持のため未実施]` と明記する）。1・2（Grep/Read）は全エージェント標準装備のため免除なし。

**承認・整形・転記も「主張」と同じ**: ユーザーの報告書・ドラフト・調査結果・主張を「確認して」「間違いない？」「整えて」「レビューして」と頼まれたときも対象。実装を読まずに「正しい」「問題ない」と言わない。文章を整えることは内容を検証したことにならない。

**下流エージェントの調査結果も「主張」と同じ**: 他エージェントが報告した調査結果・確認事項・方針をユーザーに提示する前に、根拠の `ファイル名:行番号` を自分で Read / Grep して確認する。**中継は検証ではない。** 検証できていない項目は `[未検証: {agent}報告]` を付け、確定事実として提示しない。

**環境スコープの確認**: 「実装済み／有効／存在する／直っている／権限が付与されている」と述べるときは、根拠がどの環境のものかを確認する。手元リポジトリ／sandbox ≠ 本番。確認できなければ `**[要確認: 本番反映状況]**` を付ける。データ件数・レコードの有無も同じ扱い（非本番組織の結果を本番の根拠にしない）。

**正本の判断を先にする**: コードに書いてある＝正本とは限らない。組織のランタイム状態（インストール済みパッケージ・バージョン・組織設定・機能有効化・ライセンス）はコード・コメントから推論せず、組織に直接問い合わせる。コードの挙動・仕様は実コードが正本、組織状態は組織が正本。

**適用条件の読み方**: 下表の全項目は「該当する種類の主張をする場合にのみ」確認が必要な条件付きチェックである。無関係な項目（例: 権限に触れない回答で「権限挙動」行）まで毎回確認する必要はない。

| 確認項目 | 確認方法 | 適用条件 |
|---|---|---|
| DML 挙動 | 対象 Apex の `insert / update / upsert / delete` を Read | 対象コードの DML 挙動を主張するとき |
| 自動処理のロジック内容 | Trigger/Flow/Process Builder の対象・条件・操作を Read | Trigger/Flow/Process Builder のロジック内容を主張するとき |
| **自動処理の有効化状態（Active/Inactive）** | 組織に直接問い合わせる。手元リポジトリの `<status>` タグは最後に retrieve した時点のスナップショットに過ぎず、組織側でその後 Active 化・バージョン更新されている場合がある。Flow は `FlowDefinitionView`、Trigger は `ApexTrigger` を対象組織で SOQL 確認してから「影響なし」を書く | Active/Inactive・稼働バージョンに触れる主張、特に「無効／対象外」という除外方向の結論を出すとき |
| 項目挙動 | field-meta.xml で型・required・default・formula を Read | 項目の型・必須・デフォルト・数式の挙動を主張するとき |
| 権限挙動 | 該当 permissionset/profile を Read | permissionset/profile の設定内容を主張するとき |
| **権限系の「できない／直った」の完了判定** | 対象ユーザーの全アサイン（プロファイル＋権限セット＋権限セットグループ）の和集合を確認し、異なる権限経路のユーザーを最低1人ずつ用意して実ユーザーでの Login As による UI 操作確認で完了と判定する。単一ユーザー・単一経路の確認のみで断定しない | 権限起因の不具合を「できない」「直った」と完了判定するとき |
| **課題間の関係性（同一原因か・別か）** | 両課題の該当/修正コードを Read し、対象フィールドの型・原因レイヤー・修正箇所が一致するか比較する。issue タイトル・現象の類似で同一視しない | 2件以上の課題が同一原因か否かを主張するとき |
| プラットフォーム標準仕様 | `docs/knowledge/sf-standard.md` を先に Read → 無ければ Web で裏取り（詳細は次項） | Salesforce 標準仕様（API・UI・ガバナ制限等）を主張するとき |
| **組織のランタイム状態（導入パッケージ・バージョン／組織設定／機能有効化／ライセンス）** | 組織に直接問い合わせる（Setup → インストール済みパッケージ、または Tooling API）。コード・コメント・VF タグから推論しない | 導入パッケージ・組織設定・機能有効化・ライセンスの状態を主張するとき |
| **データ件数・レコード存在・項目の有無** | 対象組織に直接実査する（`sf data query` / `sf sobject describe`）。非本番組織のクエリ結果・部分 retrieve したメタを本番の根拠にしない | データの件数・存在・有無を主張するとき |
| **メタデータ要素の実在（オブジェクト・レポートタイプ等）** | 記憶で名前を断定しない。`sf sobject list` / `sf sobject describe` 等で確認する | オブジェクト・レポートタイプ等メタデータ要素の実在を主張するとき |
| **可否判断が複数の前提の連鎖で成り立つ場合** | 前提を1個ずつ分解し、末端の前提まで個別に検証してから結論を書く。一部未検証なら「〇〇までは確認、△△は未検証」と分けて報告し `[要確認]` を付ける | 結論が複数の前提の連鎖の上に成り立つ可否判断をするとき |

**追問・反転ガード**: 「本当に？」「どっち？」「〇〇じゃない？」等の追問が来ても記憶で同調・反転しない。該当ソースを再 Read してから答える。前回答を撤回・反転する場合は、新たに読んだ根拠（`ファイル名:行番号`）を提示してから変える。同じ論点が2回以上問われた時点で、記憶ではなく必ず再 Read する。

## sf-context-loader 経由の要約コンテキスト（2層ルール）

loader は行番号を保持しないため、loader 要約からの引用はファイルパス単位で出典を示せば足りる（例: `docs/catalog/Foo__c.md`）。断定・裏付けが必要な箇所は必ず原本を直接 Read して `ファイル名:行番号` を付す。
