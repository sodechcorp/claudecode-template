# option-rollback-readiness

## 何をするか

本番リリース前にロールバック手順を最終確認する。実際に問題が発生した場合に迷わず戻せる状態を確認する。

## 実行手順

1. 今回の変更内容に対するロールバック手順を確認する（リリース手順書 release-plan.md のロールバック手順）
2. 以下を確認する:

   **コード変更のロールバック**:
   - `force-app/` は `.gitignore` 対象（各メンバーが組織から都度 retrieve する運用）のため、Git コミット履歴に基づくロールバック（`git revert` / `git reset --hard`）は機能しない
   - release-plan.md「事前記録: ロールバック用バックアップ」の retrieve が完了しているか確認する（`ROLLBACK_BACKUP_DIR` に本番の変更前状態が退避済みか）
   - 再デプロイの所要時間を見積もる（Metadata API デプロイ: 通常 1〜10 分）

   **データ変更のロールバック**:
   - データ移行を行った場合: バックアップ CSV が存在するか確認する
   - Data Loader での戻し手順が準備されているか確認する

   **設定変更のロールバック**:
   - 管理画面手動操作がある場合（本番変更の記録に、前回までの手順書で実施した管理画面の操作がある場合を含む）: 手順書の各操作に、操作直前に変更前の設定値を記録する手順と、それで戻すロールバック手順（1c）が入っているか確認する（前回までの操作は、1c で戻すものに入っているか）

3. ロールバック判断基準を確認する:
   - どんな症状が出たらロールバックするか（事前に決めておく）
   - 誰が判断するか・誰が実行するか

## 出力

release-plan.md「## ロールバック手順」節の先頭（[release-preparer.md](../../../agents/release-preparer.md) 手順書テンプレートの `{option-rollback-readiness.md による最終確認}` の位置。この枠は manual_operation_mode: false の場合のみで、true の場合は記録しない）に記録する:

- コードロールバック手順: バックアップ {事前記録の ROLLBACK_BACKUP_DIR の状態}（`{ROLLBACK_BACKUP_DIR}`）+ 再デプロイ（所要: {N} 分）
- データロールバック: {事前記録の「データのバックアップ:」の状態}
- 設定ロールバック: 該当なし / 操作直前に担当者が記録し、ロールバック手順 1c で戻す
- ロールバック判断基準: {どんな状態で判断するか}
- 担当: 判断 {氏名} / 実行 {氏名}
- 判定: ロールバック手順確認済み・リリース可 / 戻せないものあり（{事前記録で「取得できず」「取得できません」「未取得」の対象}。担当者が判断）
