# option-deployment-dependency-check

## 何をするか

デプロイの依存関係を確認する。1回のデプロイの中では Salesforce が参照の順に処理する（同じデプロイの項目・Apex クラスを、それを参照する Apex・権限セットより先に作る）ため、参照し合う資材は同じデプロイに入れればよく、順序のためにデプロイを分けない（参照先は、同じデプロイに入っているか組織に既にあればよい）。デプロイを分けるのは、デプロイの間に作業が要る場合だけ。

## 実行手順

1. 今回の変更で含まれるメタデータ種別を列挙する:
   - カスタムオブジェクト
   - カスタムフィールド
   - Apex クラス・トリガー
   - LWC / Aura
   - Flow / プロセスビルダー
   - 権限セット・プロファイル
   - カスタム設定・Custom Metadata
   - ページレイアウト・コンパクトレイアウト
   - レポート・ダッシュボード

2. **資材の外にある依存を確かめる（組織の地図があれば）**: `python scripts/python/sf-lineage/lineage.py deps --manifest <package.xml>`。資材の部品が使うカスタムの部品（項目・オブジェクト・クラス・フロー・LWC・ラベルなど）のうち、資材に入っていないものが出る。先に `lineage.py modified --target-org <本番>`（読み取りだけ）で本番の一覧を取っておくと、「✗ 本番に無く資材にも無い」＝入れないとデプロイが失敗する依存が分かる。✗ は資材に足すか、先に出す資材として手順3に回す。「？ 本番にも手元にも無い」は名前の違い・標準・管理パッケージの可能性があるので確かめる（[option-lineage-map.md](option-lineage-map.md)）
3. デプロイの間に管理画面操作・データ更新が要るものを確認する（例: デプロイしたフローが有効にならない本番で、フローを有効にしてから、それを呼ぶボタンを置いたページを出す。新しい項目に既存レコードの値を埋めてから、その項目を使うトリガーを出す）。`/release` でフローと、それを呼ぶ資材（アクション・ボタンを置いたページ等）を含む場合は、本番の `Settings:Flow` を `{tmp_dir}/prod-drift-check/flow-settings` に取得して `settings/Flow.settings-meta.xml` の `enableFlowDeployAsActiveEnabled` を確かめる（確かめられなければ false として扱う。Sandbox はソースの状態どおりにデプロイされるため確かめない）。あれば、作業の前・後でデプロイを分け、作業と、前・後に出す資材を記録する（後に出すのは、作業を前提にする資材と、それを参照する資材〔テストクラス・権限を含む〕。それ以外は前に出す）

## 出力

**呼び出し元によって出力先が異なる**:
- `/backlog` Phase B（backlog-planner.md、`_index-phase3.md` 経由）から実行した場合: implementation-plan.md に追記
- `/release`（release-preparer.md Phase 1）から実行した場合: implementation-plan.md への追記は行わず、release-plan.md「## デプロイ依存関係」に直接反映する
