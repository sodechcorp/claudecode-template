# option-cross-functional-impact

## 何をするか

リリース直前に、データ整合性と UI の一貫性への影響を最終確認する（共通コンポーネントの参照元は release-preparer Phase 2 の4.、他チーム・並行作業との競合は Phase 3 で確認するため、本 option では扱わない）。

## 実行手順

1. 変更内容のサマリーを再確認する（何を変えたか）
2. 以下の観点で横断的な影響を確認する:

   **データ整合性**:
   - 変更後のデータ状態が他の機能の処理に影響しないか
   - 新規フィールドの値が NULL / デフォルト値の場合、他の機能で問題が起きないか
   - 確認する「他の機能」は、組織の地図があれば先に `python scripts/python/sf-lineage/lineage.py who <変更した項目・部品>` の「処理」区分と「全項目・どの項目か不明の読み書き」区分から候補を出し、値の扱いはソースで確かめる（[option-lineage-map.md](option-lineage-map.md)）

   > 他チーム・進行中の別課題との競合は release-preparer Phase 3（チケット競合チェック・部品単位の照合）で確認するため、本 option では扱わない。共通コンポーネントの参照元は release-preparer Phase 2 の4.（最終資材を起点とした参照元の確認）で確認する

   **UI の一貫性**:
   - 変更した画面デザイン・操作フローが全体の UX と一貫しているか
   - 変更した項目・部品が出る画面は、`who` の「画面・帳票」区分（レイアウト・Lightning ページ・リストビュー・レポート・ダッシュボード・メール。画面・帳票は先頭8件だけ出るので `--all`）から候補を出す

3. 問題を発見した場合: リリース前に対応する

## 出力

release-plan.md「## 影響範囲サマリー」に直接反映する（`/release`〔release-preparer.md Phase 2〕専用のオプションで `_index-phase1.md` にも登録がないため、test-report.md への追記は行わない）:

**横断機能影響確認**

- 確認対象: {確認した機能・コンポーネント}
- 問題: なし / あり（{詳細・対応済み内容}）
- 最終判定: リリース可 / 追加対応要（{内容}）
