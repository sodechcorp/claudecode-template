# option-related-issue-search

## 何をするか

課題本文・コメント・ローカル `docs/decisions.md` 等で参照されている別の課題（枝番・関連課題・派生課題）を読み、その課題での対応内容・確定方針・再発パターンを把握する。キーワードで過去の類似課題を探すことはしない（docs/knowledge に記録した過去の類似課題は Phase 1 開始前に本体が渡す知識層コンテキストで見る。[_index-phase1.md](../_index-phase1.md)「Phase 1 で実行しないオプション」の option-similar-past-issue）。

## 実行手順

> 課題の読み先が保守ポータル（`{issue_source}` = `portal`）のときは、この手順の `mcp__backlog__*` を [issue-source.md](../../common/issue-source.md) §2 の対応表で読み替える。

1. 参照されている課題キーを集める（例: 「GF-347 で確定」「GF-338 で対応予定」）。Step A-2 の Backlog の課題 URL と両方に当たる課題は、先に読んだ方の結果を使う
2. 各課題を読む:
   - `mcp__backlog__get_issue` で詳細取得
   - `mcp__backlog__get_issue_comments` でコメントを**全件取得**する。件数が多い場合はページングして**最後のコメントまで取り切る**
   - コメントは**最古→最新の順に通読し**、決定が後のコメントで覆っていないか・**最新の確定方針は何か**を必ず確認する
   - 課題本文・古いコメント・ローカル `docs/decisions.md` 等の記述を最新と誤認しない（後の撤回・上書きを優先する）
3. 読んだ課題から以下を抽出する:
   - 同じ機能領域で過去に複数回の修正が入っていないか
   - 過去の修正内容・対応方針
   - 再発のパターン・根本原因への言及
   - **後のコメントで覆った決定・最新の確定方針**（特に顧客が後から「不要」「変更」と回答しているケース）
4. 発見した場合は再発防止の観点を investigation.md に追記する

## 出力

investigation.md に追記:

## 関連過去課題

| 課題 ID | 件名（要約） | 対応内容 | 再発との関連性 |
|---|---|---|---|
| ... | ... | ... | 高 / 中 / 低 / なし |

再発パターンが疑われる場合: 根本原因・再発防止の観点を記録する。
