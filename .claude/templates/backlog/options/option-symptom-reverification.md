# option-symptom-reverification

## 何をするか

報告された症状の前提（固有名詞・実データ値・操作の実在性）を確認する。コード調査・原因仮説の前に事実関係を検証することで hallucination を防ぐ。

## 実行手順

1. 課題で報告されている症状の要素を抽出する:
   - 画面名・ボタン名・フィールド名（SF UI 上の表示ラベル）
   - 操作手順（どの順序で何をした）
   - 結果（何が起きた / 起きなかった）
2. 各要素の実在を確認する。表示ラベルは症状が出た組織のもので照合する（標準オブジェクト・タブ・項目の名前も組織ごとに変えられる）:
   - **UI 要素**: 標準の機能・ボタンかどうかは Salesforce 公式ドキュメント、カスタムのもの（ボタン・アクション・ページレイアウト・Lightning ページ等）は症状が出た組織のメタデータで確認（一覧は `sf org list metadata`。ラベルは `sf project retrieve start --target-metadata-dir {一時ディレクトリ} --unzip` で取得して読み、確認後に削除）
   - **オブジェクト名・フィールド名・API 名**: 症状が出た組織に `sf sobject describe` で確認
   - **操作手順**: Sandbox で同じ操作を実際に試みる（再現できるか。使う UI 要素が Sandbox に無い・置かれていなければ「試行不可」とし、再現せずとしない）
3. 以下のパターンを特に疑う:
   - 「〇〇というボタン」が実際には存在しない UI 要素でないか
   - 「〇〇項目」が実際には別の API 名を持っていないか
   - データ側の問題（レコードの状態・フラグ値）が原因でないか
4. 確認結果を記録する:
   - 実在確認済み → 続行
   - 実在しない / 表記違い（症状が出た組織で確かめたもの）→ 課題の前提を修正して investigation.md に記録
   - 実在しない / 表記違いに見えるが症状が出た組織で確かめられない → 前提は修正せず「未確認」と記録し、課題の記載どおりの前提で続行する（investigation.md「症状前提確認」に `**[要確認: 症状前提未確定]**` 付きで記録する）

## 出力

investigation.md「根本原因 / 要件の本質」セクションの冒頭に追記:

**症状前提確認**:
- 〇〇（UI 要素名）: 実在確認済み / 表記違い（正しくは △△）/ 実在しない / 未確認（{理由}）
- 〇〇（操作手順）: Sandbox で再現確認済み / 再現せず（条件: ...）/ 試行不可（{Sandbox に無い UI 要素}）
