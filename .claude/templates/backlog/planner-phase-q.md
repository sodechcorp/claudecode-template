# Phase Q: 回答ドラフト（問い合わせ型・実装なし）詳細手順

> `backlog-planner.md` から `モード` = `回答ドラフト（Phase Q）` の場合のみ Read される。Q-1〜Q-4 の全手順・出力フォーマット・異常時の挙動を含む。

> **起動条件**: `モード` = `回答ドラフト（Phase Q）`。`種別` = `問い合わせ`（コード変更を伴わない技術回答課題）に対し、出典付きの回答文面を生成する。Phase A/B の実装判断フローとは独立したモードで、コードを書かない点は共通するが判断ポイントの提示は行わない。

### Q-1. 事前準備

`docs/logs/{issueID}/investigation.md` の存在を Glob で確認する。

**ファイルが存在しない場合**: `/backlog Phase 1（investigator）から先に実施する必要があります` とユーザに案内し、処理を中止する（`answer-draft.md` は生成しない）。

**存在する場合**: `## 課題原文（逐語記録・要約禁止）`・`## 課題サマリー`・`## 要件理解`・`## 根本原因 / 要件の本質`（問い合わせの場合「回答に必要な事実根拠」欄）・`## 業務文脈（docs/ から）`・`## 関連コンポーネント一覧` を Grep で検索し該当セクションを Read する。

### Q-2. 出典確認の強制（誤送信防止の核心）

[共通ルール参照](../../CLAUDE.md#実装裏付け出典確認全エージェント共通常に適用) — investigation.md に記載があっても、回答文面に含める事実は Read で実コードを再確認し `ファイル名:行番号` で根拠を付す。Backlog コメント・お客様発言を引用する場合は出典（お客様返信か／investigation.md からの抜粋か／自分の過去発言か）を断定する前に再確認する。

**出典を確認できない事実は回答文面の結論に含めず、`[要確認]` として別掲する。出典のない断定表現は絶対禁止**（技術回答の誤りがそのまま顧客に渡るリスクがあるため、他 Phase 以上に厳格に適用する）。

### Q-3. 回答ドラフトの生成

以下のフォーマットで `answer-draft.md` を作成する:

```
## 回答ドラフト: {issueID}

> ※これはドラフトです。内容を確認のうえ、Backlog への投稿は人間が手動で行ってください（自動投稿はしません）。

### 質問の要約
（お客様/業務担当が聞きたいことを1〜3行。業務語彙のみ）

### 回答（結論）
（結論を先頭に1〜3行。業務語彙のみ・API名は括弧補足のみ可。回答本文の冒頭と同じ文面にしない）

### 回答本文（Backlog 投稿用ドラフト）
（そのままコピーして使える丁寧な文面。結論→根拠→補足の順。業務語彙を優先し、
  相手が技術者と判明している場合（判定材料は下記「語彙」項目参照）のみ API 名を併記可。
  この節は対外送付文そのものなのでコンパクトに書く: **全体で20行以内**に収める。
  儀礼的な前置き挨拶は1〜2文に留め、区切り線・絵文字番号等の装飾は使わない。
  結論を述べたら「まとめますと」等で同じ内容を文末に繰り返さない。詳細な出典・
  [要確認]事項は本文に書き込まず「根拠」「[要確認]」「補足」の各セクションに
  逃がし、本文は要点のみで構成する）

### 根拠（出典）
| # | 主張 | 出典（ファイル名:行番号 / Backlog コメント / docs） |
|---|---|---|
| 1 | | |

### [要確認] 事項
（出典が確認できず断定を避けた点。なければ「なし」）
- [要確認] ...

### 補足
（回答に含めなかったが参考情報として記録したい点。なければ省略）
```

- **語彙**: 既定は業務担当者向け（[共通ルール参照](_README.md#-人が読む欄の日本語表示ラベル規約) と同様、API名・クラス名・変数名は使わない）。以下のいずれかが investigation.md やコメントに明記されている場合のみ「技術者」と判定し API 名を併記してよい。該当しない場合は必ず業務語彙のみとする（判定に迷う場合も業務語彙のみを既定とする）。
  - 相手の役職・肩書に「開発担当」「エンジニア」「SE」「パートナーSE」「システム担当」等の記載がある
  - 相手自身が過去のコメントで API 名・クラス名等の技術用語を使用している実績がある
  - 相手の所属が開発ベンダー・SIer と investigation.md に明記されている
- **文量**: 「回答本文」だけは対外送付文であり、他セクション（質問の要約・根拠・[要確認]）とは別基準でコンパクトに書く。**全体で20行以内**を上限とし、超える場合は根拠の詳細記載を「根拠」セクションへ逃がして本文側を削る。同じ結論を複数箇所で言い換えない・章立てごとの重複要約を作らない。「質問の要約」「根拠」「[要確認]」「補足」は内部レビュー用のためこの圧縮対象に含めない（詳しいままでよい）。
- **投稿禁止**: このエージェントは Backlog へ一切投稿しない（Write ツールで `answer-draft.md` に保存するのみ）。投稿要否・実際の投稿は `/backlog` コマンド側がチャット提示後に人間へ委ねる。

### Q-4. 完了報告

1. `answer-draft.md` を保存する
2. **保存完了をコマンド本体（呼び出し元 /backlog）に明示報告する**: コマンド本体がチャットへのドラフト全文提示・完了報告を行う（planner からは直接ユーザーに提示しない。B-4 Step 6 と同じ分担）

### Phase Q 完了の基準

以下が全て満たされていること:
- [ ] investigation.md を Read し、回答に必要な事実根拠を確認した
- [ ] 回答文面の全ての主張に出典（ファイル名:行番号 / Backlog コメント / docs）を付した、または `[要確認]` とした
- [ ] 出典のない断定表現がない
- [ ] `answer-draft.md` に保存完了し、コマンド本体に報告した

> **起動時の異常系**（investigation.md 未取得・answer-draft.md 保存失敗）は `backlog-planner.md` 末尾「## 異常時の挙動」を参照（Phase A/B と共通のため本ファイルには複製しない）。
