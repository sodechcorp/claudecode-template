# /test NG 時の戻り先テーブル

| NG の原因 | 戻り先 |
|---|---|
| 実装ミス・コードのバグ | Phase 4（実装修正） |
| 実装方針レベルの判断ミス（ClaudeCode の判断が原因。implementation-plan.md の決めた人が ClaudeCode の判断ポイント・判断ポイント化しなかったカテゴリの1行の記録、investigation.md「## 要件理解」の【ClaudeCode】の解釈を含む） | Phase 3（実装方針の再確認。ClaudeCode が判断を変える） |
| 対応方針レベルの設計ミス（approach-plan.md の【お客様】【担当者】の行・Q の回答・今回対象外、決めた人が担当者の判断ポイントが原因。承認の前提にした原因の見立て〔ClaudeCode の調査〕が崩れた場合も含む） | Phase 2（対応方針の見直し） |
| テスト仕様・期待値・シナリオ自体の誤り（製品コードは正しい） | `test-spec.md` の期待値・シナリオ・前提を修正して `/test` を再実行（**Phase を戻さない**）。製品コードが正しいと確認でき、期待値修正のみで NG が解消すると見込める場合に限る |
| 判断できない・複合原因 | ユーザに戻り先をテキストで確認（「Phase 4 / Phase 3 / Phase 2 / test-spec.md を直して /test を再実行 / 中止 のどれに戻りますか？」と質問） |

> **Phase 2 に戻すのはお客様・担当者の決定が原因のときだけ**（[CLAUDE.md §決めたことの出どころ](../../CLAUDE.md#決めたことの出どころ全エージェント共通)）。原因が ClaudeCode の判断なら、方針の見直しとして担当者に相談せず Phase 3 に戻す。担当者への提示では、原因が誰の決定か（お客様／担当者／ClaudeCode）を1行で書く。

> **テスト仕様・期待値の修正は NG 理由が明確な場合のみ行う**（実装バグを隠すために `test-spec.md` の期待結果を書き換えてはならない。`/test` の設計原則と同じ）。判断に迷う場合は「判断できない・複合原因」行に従いユーザー確認する。

戻って修正した後は **/backlog Phase 6 で Sandbox に再デプロイしてから `/test` を再実行**する。`/test` の再実行は差分モードで、撮り直すのは前回 NG・SKIP・新規の TC と、期待結果・判定方法・種別を書き換えた TC だけ（それ以外の前回 OK の TC は判定結果・証跡を流用する。オプション指定は不要で、Phase D の `judge_results.py --prev` が前回の判定をマージする）。影響範囲の TC（test.md「NG があった場合の差し戻し」手順4 の再テスト候補）のうち前回 OK のものは差分モードでは撮り直されないので、撮り直すときは `--full` で全件再テストする（TC を指定して撮り直す手段は無い）。

> 修正後は必ず **Phase 6 で Sandbox に再デプロイ**してから `/test` を再実行すること（`/test` は通常フローではデプロイしない。例外: Phase F-2 の NG 自動修正ループが発動した場合のみ、修正後の軽量再デプロイを実施する）。

## ループ上限

/test の NG 修正ループ（NG → 修正 → `/test` 再実行）は **最大 3 回まで**。4 回目に達した場合は「繰り返し NG が続いています。業務担当者との打ち合わせを推奨します」とユーザーに提案し、継続・中止の判断を求める。

**ループカウントのセッション跨ぎ保持**: `docs/logs/{issueID}/` 配下の退避済み `judgment-result.R{N}.json` の最大回次番号 N を通算カウントとする（欠番があってもファイル数ではなく最大値を基準にする＝過少カウントで上限判定が緩まないようにする）。セッションを跨いだ再開でもカウントはリセットしない。ループ上限に達した場合はユーザー確認を取る（test-report.md に「ループ上限到達」を記録してから確認）。
