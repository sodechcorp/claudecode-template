# 課題種別 → テストパターンマッピング

`/test` Phase B のテスト仕様展開（test-spec.md 生成）で参照する対応表。
`test-spec-builder`（Phase B）・`auto-evidence-runner`（オーケストレータ）でも参照する。

---

## 目的

`/test` は **テスト（動作確認）** と **エビデンス（後から人が見るための画面の記録）** を分けて考える。

| | テスト（動作確認） | エビデンス（画面の記録） |
|---|---|---|
| 目的 | 修正が正しく動くか、既存を壊していないかを確かめる | 後から人間が「確かに直っている」と目で確認できる記録を残す |
| 件数 | 課題原文と実際の変更内容から、必要なケースを**全量** | **1〜2 ケース**（主要な要求の結果が画面で分かるもの） |
| 手段 | **原則 SOQL・匿名Apex（画面を使わない）で高速に**。画面でしか確認できないものだけ UI | UI（画面操作＋スクショ） |
| 判定 | 期待値を明確にし、機械判定（判定できないものは AI が判定） | 画面の表示内容を判定（テストと同じ仕組み） |

Apex テストクラスの回帰確認・カバレッジは `/backlog` Phase 5 で実施済みのため `/test` では扱わない。メタデータ（XML/JSON）・force-app 配下のソースコードの内容確認も `/backlog` で完結しており `/test` では扱わない。

> **種別の選び方（テスト）**: 「その確認は画面を使わないとできないか？」で決める。
>
> 1. **データで結果を確認できるものは `SOQL`（必要なら `AnonApex` で処理を起動）**。処理の起動経路が画面でも、変更箇所がサーバー側（Apex・トリガー・レコードトリガーフロー・入力規則）だけで、画面が渡す入力値を匿名 Apex で同じ条件のまま再現できるなら、匿名 Apex で起動して結果を SOQL で確認する（テストの主眼は「処理が正しく動くか」であり、画面操作そのものではない）
> 2. **画面でしか確認できないものだけ `UI`**:
>    - 変更箇所が画面側にある（LWC・Aura・Visualforce・画面フロー のロジック・表示）、または画面が組み立てる入力値そのものが結果に影響する
>    - 表示される／されない、レイアウト、画面遷移、画面上の入力チェック・エラー表示・トースト
>    - 権限・共有・項目レベル権限によるユーザー視点の見え方（匿名 Apex は実行ユーザー＝管理者の権限で動くため、別ユーザーとしての見え方は確認できない。Login As で確認する）
> 3. **匿名 Apex で処理を起動したら、結果を取り直して期待値と比較する（自己検証）**。期待結果は `項目=値` または `N件` で書き、匿名 Apex は比較結果を `NG項目数={NG数}/{確認数}`（全て一致なら末尾に ` (PASS)`）の形で出力する（`auto-evidence-runner` Step 3-1 がこの形でコードを生成し、`judge_results.py` が機械判定する）。処理を元に戻す（rollback）TC は戻す前に比較し、非同期処理を投入する TC は完了を待ってから別の匿名 Apex で比較する。「例外なく終わった」だけで OK にしない（例外が起きないこと自体が期待結果の場合を除く）
>
> **エビデンスの選び方**: テストとは別に、課題の主要な要求（バグなら報告された症状が直ったこと、追加要望なら追加した機能が動くこと）の結果が画面で分かるケースを **1〜2 件** 選び、UI で画面操作してスクショを撮る。UI のテストケースが既に主要な結果を画面で示している場合は、それをエビデンスと兼ねてよい（エビデンス用のケースを追加しない）。

## 種別一覧（実行手段）

| 種別 | 実行手段 | 主な用途 |
|---|---|---|
| `SOQL` | `sf data query` | データ件数・フィールド値の確認 |
| `AnonApex` | `sf apex run --file`（匿名Apex） | データ作成・Flow起動・ビジネスロジック直接実行・結果確認 |
| `UI` | Playwright ヘッドレス | 画面表示・ボタン・遷移・ユーザ別見え方・権限差分（Login As）確認 |

## 課題種別 → 必ず当てる観点

> **発動条件（必読）**: 下表の「必ず当てる観点」は、変更が実際にその経路・処理へ及ぶ場合のみ適用する。変更の到達範囲に含まれない観点は test-spec.md 上で「[非該当] {観点}: {理由}」と1行記録してスキップしてよい（例: トリガへの1行追加が after 経路のみに影響する場合は before 経路が非該当、バルク・再帰防止は変更箇所がループ・集計・DML を含む場合のみ該当）。

| 課題種別 | 必ず当てる観点（種別） | skip 可な例 |
|---|---|---|
| バグ修正 | 再現解消（原因がサーバー側なら AnonApex（自己検証）、画面側なら UI）＋ 回帰（SOQL / UI） | 本番データ依存の再現 |
| バリデーションルール | 違反データで弾く＋ 正常データが通過（AnonApex） | 変更が当該経路に及ばない場合（理由記載） |
| トリガ | before / after 各経路 ＋ バルク 200 件 ＋ 再帰防止（AnonApex） | 変更が当該経路に及ばない場合（理由記載） |
| バッチ | `executeBatch` 起動 → 結果確認（AnonApex）＋ スコープ件数（SOQL） | スケジュール実時刻起動 |
| Flow | Flow 起動 or レコード操作（AnonApex / UI）＋ 結果（SOQL） | 外部呼出経路 |
| LWC | 画面表示・操作・エラー表示（UI: Playwright）＋ コントローラ挙動（AnonApex・自己検証） | デザイン微調整の目視 |
| 状態遷移・動的連動 | **状態変化前後の確認**（AnonApex / UI）＋ **条件分岐の負側**（UI: 表示されない側も確認）＋ **他欄変化への追従**（UI: 件数増減・選択変更で連動するか）＋ **選択時点固定の確認**（UI / AnonApex: 後から参照元を変えても値が変わらないか） | 静的表示のみの変更 |
| 権限・FLS | 該当ユーザの UI 表示差分（UI: Login As）＋ データ可視性・件数（SOQL / AnonApex） | 本番限定権限セット |
| 数式・ロールアップ | 子操作 → 親再計算 ＋ 境界値（AnonApex / SOQL） | 変更が当該経路に及ばない場合（理由記載） |
| 連携（外部） | AnonApex での実疎通確認（Sandbox） | 実外部疎通が困難な場合（要手動） |

> **上表の種別は目安**: 最終的な種別は冒頭「種別の選び方（テスト）」で決める。画面でしか確認できないものだけ `UI`、それ以外は `SOQL` / `AnonApex`（自己検証）。

> **確認観点の書き方（test-spec-builder の手本）**: 上表の観点は `test-spec-builder` が `test-spec.md` の「観点」列を書くときの参照手本となる。観点は「〜を〜すると〜になる」形の**自然文1文**で書き、オブジェクト・項目はラベル（日本語表示名）を先頭に（API名は括弧内補助のみ）。要求充足 TC は `①` `②`…、回帰 TC は `回帰` を先頭に付す。

## 権限・ユーザ切り替えテストのアーキテクチャ（Login As）

`/test` では権限・FLS/CRUD・共有ロジックの差分確認を **UI Login As の実画面（画面の動き）＋ SOQL/AnonApex（データの動き）** に一本化する。`System.runAs` を使った Apex テストクラスでの権限検証は `/backlog` Phase 5 の回帰テストが担当し、`/test` では扱わない（テストクラスの Pass/Fail は人が見ても意味が分からずエビデンス化しない）。

### UI 表示差分（権限別画面） → Playwright + Login As（管理者1認証のまま）

1. 管理者 frontdoor URL でログイン
2. 設定 → ユーザの管理 → 対象ユーザのページを開く
3. 「ユーザに代わってログイン（Login As）」をクリック
4. 対象画面でスクショ取得
5. 「{ユーザに代わってログアウト}」で管理者に戻る
6. 次のユーザへ

**前提チェック**: 組織設定「管理者によるユーザログインを許可」が有効であること（Sandbox では一般的に有効）。無効の場合は `要手動（Login As 不可）` に降格して auto-evidence-runner に記録する。

**対象ユーザ名**: test-spec 「前提・データ準備」列に対象プロファイル/ユーザを記載 → 実ユーザ名は org-profile.md から解決（不明時のみユーザー確認）。

## 判定方法の選択肢

| 判定方法 | 使いどころ | 補足 |
|---|---|---|
| `件数一致` | SOQL 結果件数が期待値と **完全一致**（デフォルト） | 余剰レコードも NG。**期待結果に「N件」を必ず書く**（書かないと機械判定できず AI 判定に回る） |
| `件数一致（以上）` | 期待件数 **以上** であれば OK | 「1件以上存在する」ことを確認するケースのみ使う |
| `含む` | SOQL 結果・Apex ログ・DOM に特定文字列が存在 | 「実際の値:」セクション内で照合。SOQL は `項目API名=値` で書くと**いずれかの行**がその値かで照合される |
| `含まない` | 文字列が証跡に**存在しない**ことを確認（否定確認） | 条件分岐の負側・非表示確認に使う。期待結果には「非表示にしたい文字列」を書く。**必ずポジティブアンカー（後述）を併記**する |
| `なし確認` | `含まない` の別名。同じ挙動 | — |
| `完全一致` | SOQL 結果の**全行**が期待値を満たす | 期待結果は `項目API名=値` で書く（例: `IsLease__c=false`。複数条件は `、` 区切り）。証跡の表の列と照合される |
| `存在確認` | ファイル・レコード・設定の存在 | — |
| `スクショ＋DOM照合` | 画面表示の確認（PNG + DOM テキスト）| 期待テキストが「実際の値:」セクション内に含まれるか機械照合。DOM .txt が必須（PNG 単独では自動判定不可・要目視） |
| `前後比較` | 状態遷移の前後で値が変わったことを確認 | 期待結果の形式: `before:変更前の値 / after:変更後の値`。before/after 両方の DOM .txt が必要 |

> **廃止**: `スクショ目視`・`PNG 存在` — 使わない。画面確認は必ず `スクショ＋DOM照合` で DOM .txt を採取する（DOM .txt が無いと機械判定できず、AI がスクショを読んで判定することになり遅い）。

> **機械判定できない場合**: 期待件数の無い `件数一致`・検証出力の無い匿名 Apex・判定方法の書き漏れ・空白に近い証跡などは、`judge_results.py` が「AI判定」とし、`/test` Phase D-2 で AI が証跡と期待結果を読んで OK/NG を確定する。人間の目視には回さない。

> **ピックリスト値（無効化された値を含む）の存在検証時の注意**: Apex/LWC の `getPicklistValues()`（UI API）は無効化された値を返さないため、無効値の存在確認 TC には使えない。ローカルの `field-meta.xml`（force-app 配下）はデプロイされる設定であり、組織の実際の状態の根拠にはならない（sandbox データを設計根拠にしないルールに抵触）。無効値を含めて検証する場合は Tooling API の `CustomField.Metadata` を使う（`sf-analyst-cat2` のオブジェクト定義書生成が使う `describe` の `picklistValues` は有効値のみのケースと無効値込みのケースがあるため、TC 設計時は個別に確認する）。

### ポジティブアンカー（空撮り・偽陽性の防止・必須）

「表示されない」「候補に含まれない」等の**否定確認（`含まない`/`非表示`/`なし確認`）**は、画面自体が正しく描画されている証拠（ポジティブアンカー）とセットでなければ意味を持たない。**空白画面・エラー画面でも対象文字列は存在しないため機械的に OK と誤判定される**ため、期待結果に必ず両方を書く:

- **ポジティブアンカー**: その画面が正常描画されたときに必ず現れる別の要素（例: 「他の候補が最低1件は表示されている」「検索結果件数が1件以上」「一覧のヘッダー行が表示されている」）
- **否定対象**: 表示されないことを確認したい文字列・要素

書き方: 期待結果に `画面描画確認: {アンカー} が表示 / 非表示確認: {対象} が非表示` の2段で書く。前提データ（候補が最低1件は出るためのレコード）が用意できない場合は UI TC ではなく前提データ準備からやり直す（空の画面を「非表示 OK」として撮らない）。

### 観点種別ごとの判定方法の選び方

| 確認したいこと | 推奨判定方法 | 種別 |
|---|---|---|
| データ件数が正確に N 件 | `件数一致` | SOQL |
| レコードが 1 件以上ある | `件数一致（以上）` | SOQL |
| 特定の文字列・値が存在する | `含む` | SOQL / AnonApex / UI |
| 特定の文字列・ボタンが **表示されない**（他の要素は表示されている中で） | `含まない`（ポジティブアンカー必須） | UI（スクショ＋DOM照合） |
| 状態が X から Y に変わった | `前後比較` | UI / AnonApex |
| 画面に特定テキストが表示される | `スクショ＋DOM照合` | UI |

## skip 可の判断基準

**原則: 判断に迷うケースは `自動` にする。要手動は以下の3類型のみ許容する**:

1. **実外部サービスへの実通信が必須**（Webhook・外部 API への実疎通が避けられない）
2. **本番限定データ・権限セットが物理的前提**（Sandbox に再現不可能な本番固有設定が必要）
3. **実時刻の到来を待たないと確かめられない**（`/test` が保存の後に待つのは5分まで）:
   - スケジュールでの起動そのもの（Apex の cron・スケジュールトリガーフローの発火）
   - 時間ベースワークフロー・プロセスビルダーのスケジュール済みアクション（予定時刻が過ぎていても最大1時間後に動く）
   - スケジュール済みパスのうち、予定時刻（基準の日時＋オフセット）を保存の4分後より前にできないもの（予定時刻の約1分後に動く。できるものは `自動` にし、基準の日時をそのパスを起動する保存の時刻からの相対で書く〔予定時刻が保存の1〜2分後になる値。過ぎた時刻にしてよいのは新規作成で起動するパスだけ。固定の日時は書かない〕）
   - そのほか時刻で動くもの（エンタイトルメントのマイルストーンアクション等）

**要手動にしてはいけないケース（= 全て自動）**:
- 画面表示・ボタン・フォーム・エラーメッセージの確認 → `UI`（Playwright）
- 複数ユーザの表示差分 → `UI: Login As`（管理者1認証で切替）
- 条件分岐ごとの挙動確認 → `AnonApex` or `UI`（分岐ごとに実行）
- Login As: 組織設定の有効/無効は**実行時に検知して初めて降格**（事前に要手動にしない）
