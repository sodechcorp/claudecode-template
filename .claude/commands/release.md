# /release [課題ID]

**引数の解釈**: `$ARGUMENTS` の先頭トークン（`--` で始まらない最初の語）を `{issueID}` とする（`backlog.md` と同一パターン）。

## 概要

`/backlog`（Sandbox リリース）・`/test`（証跡採取）完了後の独立したライフサイクル段階として、本番リリースを丁寧に確認したうえで、人間が実行する手順を1ステップずつ渡す。**本番へのデプロイ・dry-run・書き込みは一切行わない**（本番に対しては資材の取得・SELECT・画面の閲覧の read-only のみ）。

| 担当 | 主な成果物 |
|---|---|
| （本コマンド直接実行） | 前提確認・手順の1ステップずつの引き渡し（結果の記録と次の手順の組み立て直し）・Phase 7 起動 |
| `release-preparer` | リリース前の確認（最終資材での影響・チケット競合・ドリフト・差分の帰属確認）とバックアップ取得、`release-plan.md` + `release-note.md`。デプロイ後はリリース後確認と記録（Phase 7） |
| `prod-ui-verifier` | デプロイ後の本番の画面確認（閲覧・Login As での見え方。read-only）。Phase 7 の後に Step 5 から直接起動する |
| 担当者 | 本番への dry-run・デプロイの実行、保存・代表操作を伴うリリース後確認 |

## 実行手順

### Step 0: 共通 CRITICAL ルールの読込（必須・コマンド起動直後）

以下を **Read で全文読み込む**（CLAUDE.md にはスタブのみ・詳細は外出し先）:

1. Read `.claude/templates/common/verify-implementation-spec.md` — 実装裏付けルール。追加ルール記入欄まで読む
2. Read `.claude/templates/common/verify-source-attribution-spec.md` — 出典確認ルール。追加ルール記入欄まで読む
3. Read `.claude/templates/common/answer-scope-spec.md` — 回答時のスコープ管理ルール（派生事項の分離・無断リファクタ禁止）
4. Read `.claude/templates/common/uncertainty-marker-spec.md` — 確証なし時のマーカー規約（[推定]/[要確認]/[出典不明]の使い分け）

**理由**: Step 4 では main thread がユーザーの自由テキスト質問・エラー報告に直接応答する（本番デプロイ可否を左右する内容を含む）。CLAUDE.md にはスタブのみ記載のため、詳細を読まないと「挙動を実コード確認せず断定」「出典を捏造」「質問外の派生事項を無断で本文に混入」のリスクがある。`release-preparer` agent 側の Step 0c と同じ spec を読み、main thread と agent の知識を揃える（`backlog.md` Step 0 と同一パターン）。

### Step 1: 課題ID の確認

引数がない場合、チャットで確認する: 「本番リリース準備を行う課題IDを教えてください。」

### Step 2: 前提チェック

`docs/logs/{issueID}/` が存在するか（Glob）を確認する:
   - 存在しない場合: 「`{issueID}` の作業履歴が見つかりません。先に `/backlog {issueID}` を実施してください」と案内して終了

> `test-report.md` の有無確認・テスト未完時の続行可否確認は `release-preparer` Step 0b に一本化されている。本コマンドでは重複確認しない（Step 0b が未完のまま続行を希望された場合の release-plan.md 冒頭警告まで含めて処理する）。

### Step 2b: 再起動時の意図確認

`docs/logs/{issueID}/release-plan.md` が既に存在するか（Glob）を確認する:
- **存在する場合**: AskUserQuestion で確認する（question: 「`{issueID}` の本番リリース手順書は既に生成済みです。今回の実行は何が目的ですか？」/ header: 「実行目的」/ options: 「途中から再開する」〔`docs/logs/{issueID}/release-log.md` の最後の記録から Step 4 の引き渡しを再開する〕・「本番デプロイ完了を報告する」〔以降の Step 3・4 をスキップし、下記の通り Phase 7 のみを起動する〕・「手順書を再生成する」〔Step 3 へ進み通常どおり実施する。release-log.md に本番変更の記録（定義は `release-preparer.md` Phase 4 冒頭）がある場合は「本番は既にデプロイ後の状態の可能性があります」と先に伝え、前回のリリースを ③ の担当者確認まで終えているなら、先に「途中から再開する」で終えて「リリース終了:」を記録してから再生成するよう添える〕）
  - 「途中から再開する」を選んだ場合: release-plan.md と release-log.md を Read し（最後の「手順書生成:」行より後に「リリース終了:」があれば、リリースは終了済みと伝えて終える）、release-log.md の最後の「手順書生成:」行（release-preparer.md Phase 5 が書く）より後の記録だけで、完了したステップと飛ばすと記録したステップを completed として TodoWrite に復元してから（その範囲に「やり直し: Step N から」の記録があれば、それより前の Step N 以降〔手順書の並び順〕の記録は使わない）、次の未完了ステップを渡す（渡す前に、release-plan.md の最重要警告ブロックに、その範囲の「最重要警告の判断:」行で先に進む判断が記録されていない警告があれば、Step 4 の1. と同じくその警告だけを提示して判断を取る。そのうえで、② の残りに、本番変更の記録〔定義は release-preparer.md Phase 4 冒頭〕に実施が無い管理画面での操作・データ更新のステップがあれば、そのステップを question に挙げて Step 4 の4. の「デプロイされた」の後と同じ「本番の操作」の確認をし、「行われた」なら Step 4 の6. の手順書の外での実施の報告と同じく扱う。その範囲の最後の記録に次の対応〔Step 4 の6. の行、Step 5 のロールバックの判断・記録の行〕があれば、次のステップはそれ〔エラーの切り分け・選択の提示・ロールバック手順の続き等〕に従って組み立て直す）。② まで終わっている（その範囲に「本番デプロイ完了の報告:」または「Phase 7 判定:」の行がある）場合は、最後の「本番デプロイ完了の報告:」と最後の「Phase 7 判定:」のどちらよりも後に「Phase 7 記録:」の行が無ければ Step 5 の Phase 7 の起動（報告内容は最後の「本番デプロイ完了の報告:」の行のもの）から、そうでなく最後の Phase 7 判定が「OK」または「担当者作業待ち」でその後に「画面確認: 完了」も「③ の担当者確認 NG:」も無ければ Step 5 の「本番の画面確認」から、それ以外（画面確認が完了済みか ③ の担当者確認に NG がある、または Phase 7 判定が差異あり）は Step 5 の該当する扱い（差異ありの対応、または ③ の担当者確認・データのバックアップ削除の続き。最後の画面確認か ③ の担当者確認に NG があれば、③ の残りより先にロールバックの要否を確認する）から再開する（最後の Phase 7 判定〔画面確認・③ の担当者確認の NG なら最後の NG の記録〕より後に「ロールバックの判断:」やロールバックのステップの記録があれば、要否を聞き直さず最後の記録の次の対応から続ける）
  - 「本番デプロイ完了を報告する」を選んだ場合: release-log.md の最後の「手順書生成:」行より後に「リリース終了:」があれば、リリースは終了済みと伝え、追加対応のデプロイは「手順書を再生成する」で扱うよう案内して終える。無ければ、チャットでデプロイ日時（時刻まで）・結果を確認し、Step 5 と同じく release-log.md に1行追記してから、Task tool で `release-preparer` を起動する:
    ```
    task_description: 「/release 起動: {issueID} の Phase 7（リリース後確認と記録）のみを実施。デプロイ完了報告: {ユーザーからの報告内容}」
    project_dir: {プロジェクトルートパス}
    issueID: {issueID}
    ```
    以降は Step 5 の「完了報告を受けたら」と同じ手順で進める（Step 3・4 の手順書生成・引き渡しは実施しない）。
  - 「手順書を再生成する」を選んだ場合: release-log.md に本番変更の記録が無く、最後の「手順書生成:」より後に本番変更の記録の対象になる行（ロールバック等で本番変更の記録から外れたもの。あれば最終更新日時の違いはその変更による）も無く、release-plan.md「事前記録」に本番コンポーネントの最終更新日時があれば、Step 3 の前に Step 4 の4. と同じく本番と一致するかを確認する。一致しなければ Step 4 の4. と同じ AskUserQuestion で確認し、「デプロイされた」ならデプロイ日時・結果を確認して同じ1行（「Step 2（dry-run）・Step 3（本番デプロイ）完了扱い: …」）を release-log.md に記録してから Step 3 へ進む（本番変更の記録になり、release-preparer は取り直さない）。「デプロイされていない」（全体が失敗していた場合を含む）なら、一致しなかったコンポーネントを Step 3 の「取り直す前の照合」に渡す。本番に接続できない場合は、Step 3 へ進まず担当者に再認証を依頼し、認証後に確認する。手順書の管理画面での操作・データ更新のステップ（管理画面操作版〔ヘッダーの `manual_operation_mode: true`〕の操作ステップ、通常経路の管理画面手動操作、一括更新・データ移行のステップ）のうち本番変更の記録に実施が無いものがあれば、最後の「手順書生成:」より後に「リリース終了:」が無ければ、Step 3 の前にそのステップを question に挙げて AskUserQuestion で確認する（question: 「手順書の作成後に、手順書の外で{そのステップ}が本番で行われましたか（他の担当者が行った場合を含む）？」/ header: 「本番の操作」/ options: 「行われた」〔実施済みとして記録する。データのバックアップは取り直さない〕・「行われていない」）。管理画面操作版は事前記録に最終更新日時が無いため、上の照合の代わりにこの確認だけを行う。「行われた」なら、行われた操作と日時・結果を確認して操作ごとに「{Step N（要約）／管理画面手動操作・データ更新の要約} 完了扱い: 手順書の外で実施（{日時}）」（途中で失敗していれば「{同じ要約}: 手順書の外で実施、途中で失敗（{日時}。次の対応: ロールバックかそのステップだけやり直すかの提示）」。全体が失敗していれば行われていないものとして書かない）を release-log.md に記録してから Step 3 へ進む（本番変更の記録になり、release-preparer は操作後のデータを取り直さず、実施済みの操作を最重要警告とロールバック手順に載せる）
- **存在しない場合**: そのまま Step 3 へ進む

### Step 3: release-preparer への委譲

`mcp__backlog__get_issue` で `{issueID}` の課題タイトル（`{件名}`）を取得する（investigation.md・implementation-plan.md が共に無い場合の release-preparer Step 0a 側フォールバックに必要。取得できない場合は空のまま次に進む）。

Task tool で `release-preparer` を起動する:

```
task_description: 「/release 起動: {issueID} の本番リリース準備（資材確定・最終資材での影響確認・チケット競合・本番環境ドリフト検知・差分の帰属確認とバックアップ・release-plan.md 生成）」
project_dir: {プロジェクトルートパス}
issueID: {issueID}
issue_title: {件名}
取り直す前の照合: {Step 2b で渡す場合のみ、一致しなかったコンポーネント}
資材マニフェストの修正: {release-log.md の最後の「リリース終了:」行より後（無ければ全体）の「最重要警告の判断:」行に Type:Name と変更種別で書いた、加える・外す資材（同じ資材は後の行に従う）。無ければ省略}
```

### Step 4: 完了後の提示

**`release-preparer` の起動が失敗した場合**（Task エラー・完了報告が返らない場合）: 推測・要約で代替の完了報告を作成しない。エラー内容をそのままユーザーに伝えて中断する（以降の `release_plan_generated` 判定・引き渡しは行わない）。

`release-preparer` の完了報告をそのままユーザーに提示する。

完了報告に含まれる `release_plan_generated` の値で分岐する（`test-report.md` 不在時に続行を希望しなかった場合など、release-preparer が前提未達で中断した場合は `false` になる。この場合 `docs/logs/{issueID}/release-plan.md` が過去実行分として残っていても今回生成されたものではないため参照しない）:
- **`false` の場合**: 完了報告の提示のみで終了する（以降の手順は行わない）
- **`true` の場合**: `docs/logs/{issueID}/release-plan.md` を Read し、[manual-steps-todo-handoff.md](../templates/common/manual-steps-todo-handoff.md) の仕様に従って**担当者の作業を1ステップずつ**渡す（手順書全文を一度に貼らない）。release-plan.md ヘッダーの `manual_operation_mode:` 行を Grep して、管理画面操作版かどうかを先に確認する:

1. **最重要警告の確認**: release-plan.md 冒頭の最重要警告ブロック（何を警告に含めるかは release-preparer.md Phase 4 の9. が正本）に1件でも記載があれば、最初にそれだけを提示し、担当者の判断を得るまで次に進まない。判断は警告ごとに「最重要警告の判断: {警告の要約} → {判断}」の1行で `docs/logs/{issueID}/release-log.md` に記録する（Step 2b の「途中から再開する」はこの行で判断済みかを見る）。判断によっては先に進まず戻る:
   - 「他の変更が混入している疑い（手元側）」で「取り除く」→ force-app を直してから `/release {issueID}` の再実行（手順書の再生成）を案内して終了
   - 「本番の変更を上書きする疑い」で「force-app に取り込む」→ `/backlog {issueID}` に戻る（実装・テストのやり直し）よう案内して終了
   - 未リリース積み残し（その疑い）・資材マニフェスト外のコンポーネントで「含める」、または 1a で再構築した資材マニフェストに過不足がある → 判断の行に加える・外す資材（Type:Name と変更種別）を書き、`/release {issueID}` の再実行（手順書の再生成）を案内して終了（再実行の Step 3 で release-preparer に渡す）
   - 本番未接続（バックアップ等が未実施、または本番エイリアスが未確定） → 担当者に再認証（`sf org login web`）を依頼し、`release-preparer` を下記の再取得モードで起動してから進む（再取得で新たな最重要警告が返ってきたら 1. と同じく判断を取る。この警告の判断の行は再取得が終わってから書く。手順書の外で実施と記録して返された操作は completed にする〔Todo を作る前なら 3. で。途中で失敗と記録されたものは completed にせず、6. の管理画面操作・データ更新のエラーと同じく扱う〕）:
     ```
     task_description: 「/release 起動: {issueID} の Phase 4 のバックアップ・差分の帰属確認のみ再実施（理由: {本番未接続からの復旧 / バックアップ取得後の本番の変更}）」
     project_dir: {プロジェクトルートパス}
     issueID: {issueID}
     ```
2. **Claude が確認済みの項目**: ① の【Claude確認済】（テスト完了・資材マニフェスト・影響確認・チケット競合・ドリフト・差分の帰属確認・バックアップ〔取得した項目・件数・保存先・削除予定を含む〕）は、結果を3〜5行にまとめて一度だけ伝える（Todo にしない）
3. **担当者の作業を Todo にする**: ① の【担当者】→ ② の `### Step N: ...`（通常経路では Step 1 は Claude が実行するため除く。**管理画面操作版は Step 1 から担当者の操作なので全て含める**）＋管理画面手動操作 の順に TodoWrite でタスク化する（③ はデプロイ完了後に Step 5 で扱う）。1. で実施済みの操作（release-preparer.md Phase 4 の9.）を再実行しないと判断したときは、判断の行に続けて release-log.md に「{Step N または操作の要約}: 飛ばした（実施済みのため再実行しない）」を書き、ここで completed にする
4. **② Step 1（バックアップの最新確認）は Claude が実行する**（通常経路のみ）: **dry-run のステップを渡す直前と、本番デプロイ（Step 3）のステップを渡す直前**に、[prod-readonly-check.md](../templates/common/prod-readonly-check.md) で本番接続を確認し、資材マニフェストの本番コンポーネントの最終更新日時（`sf org list metadata`。一覧の取り方は [option-org-drift-check.md](../templates/backlog/options/option-org-drift-check.md) Tier 1 の「一覧に出ない資材」に従う）が release-plan.md「事前記録」のコンポーネントごとの `lastModifiedDate` と一致するかを確認する（「一覧に出ないため対象外」の資材は確かめない）。デプロイを分けた手順書（Step 2-1・Step 3-1・…）では、次に渡すデプロイの資材だけを確かめ、この 4. と 6. の Step 2・Step 3 は、そのデプロイの Step 2-{k}・Step 3-{k} と読む（前のデプロイで出した資材は、そのデプロイで更新されている）。あわせて、資材マニフェスト分の force-app が `docs/logs/{issueID}/release-snapshot/` と一致するかも確認する（手順書作成後に force-app が取り直されていないか）。
   - 本番の最終更新日時が一致しない → 先に、一致しないコンポーネントと最終更新者・日時を示して AskUserQuestion で確認する（question: 「{コンポーネント}が手順書作成後に本番で更新されています（{最終更新者}・{日時}）。手順書の外で今回の資材が本番にデプロイされましたか（他の担当者が変更セット等で行った場合を含む）？」/ header: 「本番の更新」/ options: 「デプロイされた」・「デプロイされていない」）:
     - **デプロイされた**: 再取得しない（rollback-backup/ などリリース前の状態を上書きしない）。デプロイ日時（時刻まで）・結果を確認し（全体が失敗していた場合は「デプロイされていない」と同じ扱いにする）、release-log.md に「Step 2（dry-run）・Step 3（本番デプロイ）完了扱い: 本番デプロイ成功（手順書の外で実施、{デプロイ日時}）」（最後のデプロイなら「・Step 4（デプロイ結果確認）」を Step 3 の後に加える。Step 4 は手順書のデプロイの結果を手元の CLI で確かめるステップで、手順書の外のデプロイの結果は Phase 7 で確かめる）と記録してそれらを completed にする。② の残りに、本番変更の記録に実施が無い管理画面手動操作・データ更新のステップがあれば、Step 2b と同じ「本番の操作」の確認をし、「行われた」なら 6. の手順書の外での実施の報告と同じく扱う。そのうえで ② の残りを通常どおり渡す
     - **デプロイされていない**: 2つ目以降のデプロイの直前（前のデプロイが本番に入った後）なら、再取得モードは起動しない（前のデプロイで出した資材を手順書の外でのデプロイと取り違え、残りの資材のバックアップも本番変更の記録があるため取り直されない）。一致しないコンポーネントは他の変更として、そのデプロイを進める（他の変更を上書きする）か、6. の本番が途中まで変わった状態のエラーと同じくロールバック手順に進むかを担当者に確認する（どちらでも、ロールバック手順 1 はそのコンポーネントを手順書作成時のバックアップで戻すため、他の変更も戻ることを添える）。それ以外で Step 3 の直前に不一致を検知した場合は、再取得の前に release-log.md に「やり直し: Step 2 から」と記録し、取り直した後は dry-run（Step 2）からやり直す。`release-preparer` を上記1.の再取得モードで起動し、取り直した結果（差分の帰属確認・データの再取得・手順書の外で実施と記録した操作を含む。その操作は 1. と同じく扱う）を伝える。**新たな最重要警告が返ってきたら 1. と同じく担当者の判断を取ってから進む**。取り直す前の照合で「手順書の外でデプロイ済み」が返った場合は、これらに代えて上の「デプロイされた」と同じ扱いにする
   - force-app が release-snapshot と一致しない → 手順書作成後に force-app が変わっているため、そこで止めて `/release {issueID}` の再実行（手順書の再生成）を案内する
   - 本番に接続できない → 次に進まず、担当者に再認証を依頼する
5. 先頭の未完了ステップのみ内容（コマンド）を提示し、「実行結果を教えてください」と添える（管理画面での操作のステップで、本番変更の記録にその実施〔途中で失敗を含む〕があれば、手順書の「操作直前に変更前の値を記録する」の代わりに release-preparer.md Phase 5 の実施済みの ⚠️〔今の値は操作後の値のため記録し直さない〕を添える）
6. **報告を受けたら**: 結果を `docs/logs/{issueID}/release-log.md` に1行追記し（日時・ステップ・報告内容・次の対応。次の対応は Step 2b の再開が使うため、次に渡すステップ・提示する内容を具体的に書く）、**結果に合わせて次のステップを組み立て直す**:
   - 成功が明確 → Todo を completed にして次のステップへ（成否が不明瞭な報告は completed にせず確認する）
   - dry-run でエラー → エラー文を読み、release-plan.md「dry-run/デプロイが失敗した場合の切り分け」に従って原因を特定し、本番デプロイのステップは出さない。本番固有の原因なら解消後に `/release {issueID}` を再実行、実装起因なら `/backlog` への差し戻しを案内する
   - 本番デプロイ（Step 3）でエラー → 本番へのデプロイは全体が取り消されるため本番は変わっていない。dry-run のエラーと同じ切り分けに進む（ロールバックは不要）
   - 管理画面操作版の操作ステップ・管理画面手動操作・データ更新のステップ・デプロイを分けた手順書の2つ目以降のデプロイの dry-run・本番デプロイ（Step 2-2・Step 3-2 等。上の2つに代えてこちら）でエラー → 本番が途中まで変わっている状態のため、release-plan.md「ロールバック手順」を次のステップにするか、そのステップだけやり直すかを原因とあわせて提示する。ロールバックにした場合は ② の残りを渡さず（completed にもしない）にロールバック手順を1ステップずつ渡し、終わったら Step 5 の差異ありの「不要・出し直す」と同じく戻り先を決めて記録し、記録済みの行を書いてから案内する（`prod-release-issue.md` は既存を R{N} へ退避して新規作成し、`docs/decisions.md` とともに release-preparer.md 7-4 の「それ以外」の2ファイルの書式で書く。結果は「一部失敗（{エラーになったステップ}でエラー）」、ロールバック状況はロールバックの結果）
   - 状況が変わって不要になったステップは理由を記録して飛ばす。ただし、本番デプロイ（Step 3）・管理画面での操作・データ更新のステップ（ロールバック手順のステップは除く）が手順書の外で既に行われていた（他の担当者が行った場合を含む）という報告は飛ばさず（「飛ばした」は本番変更の記録にならず、後の再生成・再取得が実施済みとして扱わないため）、行われた日時（時刻まで）・結果を確認する。全体が失敗していれば、行われていないものとして Todo を未完了のまま残す。本番デプロイは、冒頭の1行の代わりに 4. の「デプロイされた」と同じく扱う（日時が事前記録の rollback-backup/ の取得日時より前か、時刻が無く前後が決まらなければ、その1行の「手順書の外で実施」を「手順書の外で実施・バックアップの取得前」にし、先に release-plan.md のロールバック手順に release-preparer.md Phase 5 の「バックアップの取得より前にデプロイされています」の ⚠️ を同じ位置に書き足す〔1b の直下に付けるかを決められなければ付ける〕。バックアップがそのデプロイの後の状態のため）。管理画面での操作・データ更新は、先に release-plan.md のロールバック手順に release-preparer.md Phase 5 の「手順書の外で実施されました」の ⚠️ を同じ位置に書き足してから（既にあれば重ねない）、冒頭の1行の代わりに Step 2b と同じ行を書き、完了扱いなら completed にし、途中で失敗なら上の管理画面操作・データ更新のエラーと同じく扱う
7. ② の全 Todo が completed になったら「本番デプロイが完了したら教えてください（Claude がリリース後確認を行います）」と一言添える

### Step 5: 本番デプロイ完了報告を受けての Phase 7 起動

**本番デプロイ完了の報告を受けた場合**（本セッション継続中のみ。`/release {issueID}` 再起動時は Step 2b で判定済み。release-log.md の最後の「手順書生成:」行より後に「リリース終了:」があれば、追記せず Step 2b の「本番デプロイ完了を報告する」と同じく案内して終える）: 報告内容を `docs/logs/{issueID}/release-log.md` に「本番デプロイ完了の報告: {デプロイ日時・結果}」の1行で追記してから、Task tool で `release-preparer` を再起動し、Phase 7（リリース後確認と記録）のみを実施させる:
```
task_description: 「/release 起動: {issueID} の Phase 7（リリース後確認と記録）のみを実施。デプロイ完了報告: {ユーザーからの報告内容}」
project_dir: {プロジェクトルートパス}
issueID: {issueID}
```

**完了報告を受けたら**: リリース後確認（資材の一致・削除の反映・状態確認・想定外の変更）の結果を伝える。
- **差異あり**: ロールバックの要否を担当者に確認する（不要なら、差異を直して出し直すか、差異を受け入れて進めるかも聞く）。判断は「ロールバックの判断: {要／不要・出し直す／不要・受け入れ（{理由}）}（次の対応: {…}）」で release-log.md に記録する。画面確認（下記）は行わない
  - **要**: release-plan.md「ロールバック手順」を1ステップずつ渡し、各ステップの結果を Step 4 の6. と同じ形で release-log.md に1行ずつ記録する。終わったら下の「不要・出し直す」と同じく記録して案内する
  - **不要・出し直す**（要のロールバック後も同じ）: 原因から戻り先を決め（通常経路は release-plan.md「dry-run/デプロイが失敗した場合の切り分け」の戻り先と同じ区分で、本番固有なら解消後に `/release {issueID}` の再実行、実装起因なら `/backlog {issueID}` の Phase 4 から。管理画面操作版は、本番固有なら同じく再実行、操作手順・方針の誤りなら `/backlog {issueID}` の Phase 6〔操作手順の作り直し〕または Phase 2〔対応方針〕から。手順書にこの切り分けの節が無いため、原因を伝えて担当者と決める）、`prod-release-issue.md`（ロールバック状況と差し戻し理由・差し戻し先〔上の区分と戻り先〕。退避しない）と `docs/decisions.md` の当該課題エントリ（「ロールバック状況」）に追記して、release-log.md に「ロールバックの記録: 済（ロールバック状況: {全ステップ完了／一部〔…〕／不要}。次の対応: {戻り先の案内}）」を書いてから案内する（Step 2b の再開が記録をやり直さないように）
  - **不要・受け入れ**: `prod-release-issue.md` と `docs/decisions.md` の当該課題エントリに「ロールバック状況: 不要（差異を受け入れ: {理由}）」を追記し（decisions.md の「リリース予定日 / 担当」欄と changelog.md は 7-4 のまま更新しない）、release-log.md に「画面確認: 未実施（差異を受け入れ。全行〔{V番号}〕を担当者の確認に回した。次の対応: ③）」を書いてから、③ の担当者確認・データのバックアップ削除へ進む（画面確認の行は、差異を知っている担当者が見る方が差異による違いを NG と取り違えない）。Phase 7 の差異のうち担当者の作業で説明できるもの（有効化等）は受け入れの対象にせず、その作業を ③ に含めて渡す（その作業に依存する画面確認の行は、その作業の後に渡す）
- **未実施（本番未接続）**: 担当者に再認証を依頼し、認証後に Phase 7 をやり直す。画面確認（下記）は行わない
- **OK・担当者作業待ち**: 下記「本番の画面確認」を実施してから、release-plan.md「③ リリース後チェック」の担当者の確認項目（担当者作業待ちの内容〔フローの有効化等〕を含む）を Step 4 と同じ方式で1つずつ渡し、結果を release-log.md に記録する
- **既に本番リリース実施記録済み**（同じデプロイの Phase 7 が記録済み）: release-log.md の最後の Phase 7 判定より後に「画面確認: 完了」も「③ の担当者確認 NG:」も無ければ下記「本番の画面確認」から、あれば ③ の担当者確認・データのバックアップ削除の残りの続きから進める（その画面確認か ③ の担当者確認に NG があれば、③ の残りより先にロールバックの要否を確認する。ロールバックの判断・ステップの記録があれば、Step 2b と同じくその続きから）

**本番の画面確認（release-log.md の最後の Phase 7 判定が「OK」または「担当者作業待ち」のときのみ・確認不要で自動実行）**: release-plan.md「③ リリース後チェック」の「Claude が実施する確認（画面…）」表を Read する。表が 1 行以上あり、release-log.md の最後の Phase 7 判定より後に「画面確認: 完了」の記録がまだ無い場合に、Task tool で `prod-ui-verifier` を起動する（表が「該当なし」なら起動しない。「画面確認: 未実施」の記録は完了ではないので起動する）。最後の Phase 7 判定が「担当者作業待ち」なら、その作業（フローの有効化等）に依存する行を `manual_rows` で渡し、作業が済むまで実行させない（要手動として担当者の確認に回す）:
```
task_description: 「/release 起動: {issueID} のリリース後画面確認（read-only）」
project_dir: {プロジェクトルートパス}
issueID: {issueID}
prod_alias: {release-plan.md ② の --target-org の値。manual_operation_mode: true の場合は「対象環境:」行の値。Phase 7 の完了報告の「対象環境」と同じ}
checks_source: docs/logs/{issueID}/release-plan.md
evidence_dir: docs/logs/{issueID}/release-verification
manual_rows: {担当者作業待ちの作業に依存する行の V 番号と作業の内容。無ければ「なし」}
```
起動が失敗した場合は、推測で結果を作らず、エラー内容をそのまま伝え、画面確認の全行を ③ の担当者の確認に加えて渡す（「画面確認: 未実施（起動失敗。全行〔{V番号}〕を担当者の確認に回した）」と記録する。③ を続きから渡すときもこの V 番号で加える）。返却を受けたら結果を `docs/logs/{issueID}/release-log.md` に次の形式で 1 行追記し（NG があれば、下記の prod-release-issue.md・decisions.md への記録を済ませてから書く）、次のとおり扱う（`[SKIP]` が返った場合も、理由を「画面確認: 未実施（対象項目なし／Sandbox）」の形で記録するだけで、以降の処理は不要）:
- 記録形式: 「画面確認: 完了（OK a / NG b / 要手動 c〔担当者の確認に回した行の V 番号。担当者作業待ちに依存して実行しなかった行は、その作業も添える〕）」または「画面確認: 未実施（理由）」
- **OK**: 件数と証跡の保存先だけを一度伝える
- **NG**: `docs/logs/{issueID}/prod-release-issue.md`（既存があれば `prod-release-issue.R{N}.md` へ退避してから新規作成。release-preparer.md 7-4 の「それ以外」と同じ規約）に NG の内容を記録し、`docs/decisions.md` の当該課題エントリに「本番リリース後の画面確認で NG（{V番号・画面名・差の種類}）。詳細は prod-release-issue.md 参照」と追記する（リリース予定日／担当欄・changelog.md の本番リリース行は実施済みのまま変更しない）。そのうえで画面・期待・実際の差の種類を伝え、Phase 7 の「差異あり」と同じく担当者にロールバックの要否を確認する（判断の記録とその後の扱いも同じ。ただし「不要・受け入れ」は「ロールバック状況」を追記した後、画面確認の行を加え直さずに ③ の続きへ進む）。**decisions.md には V 番号・画面名・差の種類だけを書き、レコードの値・氏名は書かない**
- **要手動**: 理由（Login As 不可・ユーザー特定不可・遷移不可・状態変更を伴う・担当者作業待ちに依存）を伝え、その項目を ③ の担当者の確認に加えて 1 つずつ渡す（担当者作業待ちに依存する行は、その作業の後に渡す。③ を続きから渡すとき〔Step 2b の再開・上の「既に本番リリース実施記録済み」〕も、最後の Phase 7 判定より後の画面確認の記録の V 番号で加える）
- **未実施（本番未接続・画面にログインできない）**: 担当者に再認証（画面にログインできないときは返却の理由のとおり。パスワードの期限切れなら接続ユーザーのパスワード変更）を依頼し、済んだら画面確認だけをやり直す
- スクリーンショットには実顧客のデータが写る可能性がある旨を、初回の結果報告で一言添える（個人情報の扱いは [prod-readonly-check.md](../templates/common/prod-readonly-check.md)「本番 UI 確認」の証跡の扱いに従う）

**③ の担当者確認で NG が報告されたら**（保存・代表操作で期待どおりに動かない等）: ③ の残りとデータのバックアップの削除より先に、上の画面確認の NG と同じく `prod-release-issue.md`・`docs/decisions.md` に記録してロールバックの要否を確認する（decisions.md には「本番リリース後の担当者確認で NG（{確認項目・差の種類}）。詳細は prod-release-issue.md 参照」と書く。最後の Phase 7 判定が差異ありか、その後に NG が1件以上の画面確認の記録か「③ の担当者確認 NG:」の行があれば、今回のデプロイの prod-release-issue.md が既にあるので退避せず追記する）。release-log.md の ③ の結果の行は、この記録を済ませてから「③ の担当者確認 NG: {確認項目}（次の対応: ロールバックの要否の確認）」と書く。「不要・受け入れ」はロールバック状況を追記して ③ の続きへ進む（「画面確認: 未実施」の行は書かない）。

**③ の担当者確認が全て終わったら**: データのバックアップ（`docs/logs/{issueID}/backup/data/` と、再生成で退避した `backup/data.R*/`）が存在する場合は削除する（個人情報を含みうるため残さない）。[cleanup-rules.md](../spec/cleanup-rules.md) に従い `ignore_errors=True` を使わずに削除し、削除後に存在しないことを確認してから「データのバックアップを削除しました」と伝える（削除に失敗した場合はパスを示して担当者に手動削除を依頼する）。メタデータの `rollback-backup/`・`release-snapshot/` は個人情報を含まないため残す。変更前の写し（`docs/logs/{issueID}/before-snapshot/`）は削除する（追加対応で `/backlog` が変更前の写しを取り直すため）。画面確認の証跡（`release-verification/`）は削除せず残すが、実顧客のデータが写る可能性があるため、チャット・Backlog・共有ドライブへ載せる前に写り込みを確認する（`docs/logs/` は git 管理外）。最後に release-log.md に「リリース終了: {日時}」を1行追記する（本番変更の記録〔release-preparer.md Phase 4 冒頭〕はこの行より前の記録を見ない）。

## 注意事項

- **本番デプロイは本コマンドの範囲外**。`release-plan.md` に記載された CLI コマンド（`deploy_route: manual-operation` の場合は管理画面操作ステップ）は人間が手動で実行する
- 課題間の並行対応でチケット競合が検出された場合、または本番環境ドリフトで「競合・要人間判断」が検出された場合は、release-preparer の完了報告で明示的に警告される。警告を無視してデプロイしないこと
- 本番組織への接続は read-only に限る。`release-preparer` 内部（Phase 1・Phase 4・Phase 7・バックアップ再取得モード）と `prod-ui-verifier`（Step 5 の画面確認。閲覧・Login As のみ）のほか、本コマンドも Step 2b（手順書の再生成前の確認）と Step 4 の4.（バックアップの最新確認）の `sf org list metadata`、ロールバック手順 1b の照合・作られたレコードの件数の `sf data query`（SELECT）だけを `prod-readonly-check.md` を通して実行する
